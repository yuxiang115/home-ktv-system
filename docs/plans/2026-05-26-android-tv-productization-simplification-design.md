# Android TV 产品化与流程简化设计

**日期:** 2026-05-26
**目标:** 在真实歌库、真实 NAS、真实电视播放已经跑通后，把系统从“能验证”推进到“日常可用、可部署、可维护”。

## 背景

当前系统已经从 Web TV 调试端转向 Android TV + libVLC 作为正式播放端。真实歌曲来自 PostgreSQL `ktv_*` 索引和 NAS `/mnt/nas/KTV歌曲`，手机控制器可以搜索、点歌、切歌，电视端可以播放真实 MV 并切换音轨。最近又补齐了二维码入场、播放页简化、单音量控制、项目结构文档和本地部署说明。

下一阶段不应该继续堆功能，而应该按真实使用链路补齐产品化能力：启动配置、安装发布、异常恢复、真实曲库运维、部署 smoke，以及一次专门的代码和流程简化。

## 方案比较

### 方案 A：继续按问题逐个修

优点是最快响应当前 bug。缺点是规划会继续漂移，Web TV、旧双 Asset 思路、真实 MV、Android TV、在线补歌等历史路径会混在一起，后续维护成本会越来越高。

### 方案 B：一次性大重构

优点是理论上可以快速清理历史包袱。缺点是风险过高，真实播放链路已经可用，不适合在没有完整回归证据时大面积改协议和数据库流程。

### 方案 C：里程碑驱动的产品化推进

先冻结当前可用基线，再依次做 Android TV 配置持久化、发布安装、韧性诊断、代码流程简化、后台真实歌库运维和生产部署 smoke。简化工作单独成章，先审计、再验证、最后删除或收敛。

**采用方案 C。** 它能保持系统可用，同时把之前探索期留下的接口和流程债务有序收口。

## 下一阶段结构

### 1. 基线验收

先把当前 Android TV + Mobile + API + Admin 的真实播放链路作为基线：搜索、点歌、切歌、音轨切换、音量、二维码入场、后台在线状态和真实歌曲队列。任何后续修改都要能回归这条主链路。

### 2. Android TV 启动与配置持久化

电视端需要更像一个产品：记住上次 API 地址、房间、设备名；无启动参数时进入配置/扫码指引；网络或 API 异常时给出明确状态，而不是依赖 adb 命令重新注入参数。

### 3. APK 发布、签名和安装流程

建立 debug/release 两套可重复构建方式，补充版本号、签名配置、安装命令、真实电视更新步骤和最小回滚方式。目标是用户可以稳定把 APK 放到电视上测试和更新。

### 4. 播放韧性和诊断

覆盖真实使用中最容易出问题的地方：后端重启、电视断网、NAS 文件不可读、播放失败、音轨切换失败、控制器退出后重进。诊断不做复杂自动判断，优先展示原始证据和可执行恢复动作。

### 5. 代码和流程简化

这是独立章节。原则是“有证据再删”：先列出可能已经不需要的接口、字段、UI、命令和流程，再用搜索、测试和真实链路验证依赖关系。重点检查：

- Web TV 是否降级为调试端，哪些正式路径应迁移到 Android TV。
- 真实 MV 单 Asset 模型落地后，历史双 Asset/切换路径是否还有必要。
- 在线补歌流程是否仍属于当前核心产品，哪些入口应隐藏、降级或保留为实验能力。
- 房间状态、snapshot、控制命令、TV telemetry 是否存在重复字段或重复转换。
- 部署脚本是否可以从多套 env 入口收敛成一个真实模式 profile。

### 6. 后台真实歌库运维

Admin 需要服务真实使用：查看索引歌曲来源、文件可读性、音轨数量、音轨角色、重新检查单曲、批量抽样健康检查。它不是 CMS，而是“排查和修复真实歌库问题”的工作台。

### 7. 生产部署和 smoke

把本地真实场景部署变成一个可重复流程：启动、日志、健康检查、控制器地址、Android TV 安装、真实歌曲 smoke、失败场景 smoke。最终产物是 README 可执行步骤和自动/半自动验证脚本。

## 非目标

- 不做多房间。
- 不做账号权限。
- 不做唱歌评分和实时 DSP。
- 不做强制转码方案；必要时作为后续兜底里程碑。
- 不把 Admin 做成大型 CMS。

## 成功标准

- 用户可以用一套明确步骤部署 API/Admin/Mobile/Android TV。
- 真实电视上扫码点歌、播放、切歌、音轨切换和音量控制稳定可用。
- 主要异常都有中文提示和排查入口。
- README、部署文档、Android TV 文档和项目结构文档一致。
- 简化章节产出明确结论：删除什么、保留什么、降级什么，以及对应验证证据。
