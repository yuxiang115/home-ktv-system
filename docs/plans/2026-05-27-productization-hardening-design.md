# 产品化收口设计

## 背景

HomeKTV 当前已经具备真实歌库、Android TV 播放、Web TV 调试、手机控制器、后台和 Docker 服务器部署能力。下一阶段最重要的风险不是单个功能缺失，而是“环境不可复现、故障不可定位、仓库状态不清晰、真实曲库质量不可治理”。

本设计只覆盖可以在不追加产品决策的情况下完成的收口工作。涉及账号体系、多房间商业化、曲库人工审核策略、转码兜底策略等问题，先记录为待决项。

## 目标

1. 让服务器从 Git 拉取后能用固定命令完成部署、自检、查看状态、排障。
2. 让本地仓库能清楚区分正式代码、运行产物、历史实验和待收口内容。
3. 让真实环境问题先被脚本发现，而不是等到手机或电视端报错。
4. 让后续开发以 Web TV 做快速验证、Android TV 做实机验证的流程变得明确。

## 推荐方案

采用“轻量产品化硬化”：

- 不引入新的运维平台，不拆服务，不增加队列系统。
- 在现有 `deploy/docker/ktv.sh` 和 `deploy/source/ktv.sh` 下增加统一 `doctor` 自检入口。
- 新增独立 Node 脚本负责自检逻辑，Docker 和源码部署共用。
- 补充长期有效文档，记录 lxc-dev、Caddy、Homepage、NAS bind mount、验证步骤和故障排查。
- 新增仓库卫生检查脚本，先报告风险，不自动删除或移动历史文件。

## 自检范围

`doctor` 做本地可验证的原始指标检查，不替代人工判断：

- 环境文件是否存在，关键变量是否配置。
- `PUBLIC_BASE_URL`、`CONTROLLER_BASE_URL`、`CORS_ALLOWED_ORIGINS` 是否覆盖 Admin、Controller、Web TV。
- Docker 部署的 compose 配置是否可渲染。
- Docker 服务状态和 API `/health` 是否正常。
- NAS 宿主机路径是否存在且可读。
- 媒体路径映射是否包含真实索引路径 `/mnt/nas/KTV歌曲`。
- 公网或内网 URL 是否返回 HTTP 成功状态。

## 仓库卫生范围

仓库卫生检查只做报告：

- 当前工作区是否有未提交修改。
- 是否存在未跟踪源码、迁移、文档或报告。
- 是否存在运行产物目录。
- 是否处在 main 分支且落后/领先远端。

这一步不自动修复，因为当前存在一些历史索引文件需要人工判断是否正式入库。

## 待决项

- Admin 是否需要登录鉴权，以及采用什么方式。
- 真实曲库治理工作台的审核流程：自动推断后直接 ready，还是必须人工确认一部分样本。
- 单音轨歌曲在控制端的展示策略。
- Android TV APK 发布和自动更新策略。
- 是否需要对公网媒体流做访问控制。
